# 说准一点：产品与系统设计

- 状态：产品方向已实施为静态首版；此文保留为产品与内容模型基线
- 日期：2026-10-31
- 对应任务：Task Constitution T1、T2、T3
- 设计目标：让不熟悉 UI 术语的人从自己的表达出发，找到合适的交互模式，并把真实需求转成 AI Coding 可执行的指令。

## 1. 产品判断

用户通常不会先想起 `Combobox`、`Alert Dialog` 或 `Disclosure`。他们会说“给我一个选择框”“点一下以后告诉我成功了”“把详情从旁边拉出来”。系统应从这些表达和用户要完成的事开始，再通过少量问题解释多个可能模式的区别。

核心关系是：

```text
新手口语 / 产品需求
        ↓
用户目标与关键条件
        ↓
多个可选交互模式及选择理由
        ↓
术语解释 + 可操作示例 + 精准 AI 指令
```

一个口语入口不必只对应一个术语。相反，同一个交互模式也可以出现在多个不同的需求入口里。因此内容关系采用“多入口到多模式”，并让每条推荐关系带有能读懂的理由。

## 2. 目标用户与需要完成的事

| 用户 | 当前困难 | 希望完成的事 |
|---|---|---|
| 新手产品经理 | 知道业务目的，但只能说“加个弹窗”“做个下拉框” | 发现关键交互差异，写出产品需求或验收标准 |
| AI Coding 新手 | 不确定怎样把想法告诉 AI，也不知道组件名称 | 看见可操作的例子，复制并修改一段清楚的指令 |
| 项目贡献者 | 想补充术语，但容易只添加名词解释 | 按统一模型补齐口语入口、选择条件、模式差异和示例 |

产品不是词典查词练习。读者需要能回答：用户在做什么、界面何时响应、有没有选择、会不会阻断、结果怎样结束。

## 3. 产品原则

1. **从用户目标开始**：首屏用“我想让用户……”或新手原话引导探索。
2. **先解释差异，再教名称**：每个模式都说明“什么情况下适合它”。
3. **模糊时给候选项**：展示少量可比较的结果和推荐理由；必要时再问一题。
4. **指令描述行为**：术语只是提示，指令还应写清触发、位置、选择规则、关闭方式和状态。
5. **例子可以操作**：读者能够直接体验打开、选择、关闭、报错或状态变化。
6. **不用技术背景也能贡献**：内容作者主要填写表单式字段和 Markdown 说明，不必编写决策代码。
7. **静态优先、隐私默认**：首版无需账号、后端、模型 API 或分析脚本，所有需求选择在浏览器本地处理。

## 4. 信息架构

### 主入口：按我想让用户完成的事来找

| 需求入口 | 新手常用表达示例 | 要回答的主要问题 |
|---|---|---|
| 让用户输入或修改 | “给个文本框”“让用户写一下” | 内容长短、是否搜索、是否私密、是否从已有选项中挑选？ |
| 让用户选择或设定 | “加个选择框”“让他勾一下” | 单选还是多选、选项多少、是否要搜索、是否立即生效？ |
| 让用户执行操作或前往别处 | “加个按钮”“点这里去详情” | 执行动作还是导航、是否主要操作、是否危险、是否有次级操作？ |
| 告诉用户发生了什么 | “提示一下”“报错给我看” | 成功、错误还是提醒？要停留多久？是否需要用户处理？ |
| 临时展示补充内容 | “弹出来”“从旁边拉开详情” | 需要决定吗？阻断背景吗？有锚点吗？从哪个边缘展开？ |
| 浏览、切换和展开内容 | “分几块切换”“点一下再展开” | 同屏展示、互斥切换还是分步查看？ |
| 查找、筛选和整理内容 | “列表里找一下”“加几个筛选条件” | 查关键字、缩小范围、改变排序还是比较记录？ |
| 呈现页面状态 | “加载时显示一下”“没数据怎么办” | 正在加载、首次为空、搜索无结果、失败还是已完成？ |

主导航建议为“按需求找”“所有说法”“术语索引”。其中“按需求找”是首页主要入口；术语索引服务于已经知道名称、希望快速查找的人。

### 产品功能分层

| 优先级 | 功能 | 读者得到什么 |
|---|---|---|
| P0 | 口语入口与场景搜索 | 可以按“我想让用户……”或常用说法找到相关需求族 |
| P0 | 澄清问题与模式推荐 | 用少量具体问题缩小候选范围；每个结果都解释推荐原因 |
| P0 | 候选比较与关系跳转 | 并排比较相近模式，并查看“如果条件不同，应该选什么” |
| P0 | HTML 交互示例 | 直接体验触发、选择、提交、关闭和异常状态 |
| P0 | 指令生成器 | 把用户目标、行为约束和模式说明整理成可编辑、可复制的指令 |
| P0 | 术语索引与反向查找 | 已知英文术语、中文俗称或别名的读者仍能快速定位相关需求 |
| P0 | 贡献说明与内容约定 | 贡献者能按内容契约添加说法、分支、模式和示例关联 |
| P1 | 组合需求 | 例如“搜索并选客户”可以输出 Search Field + Combobox + Empty State 等组合 |
| P1 | 场景练习 | 给出模糊需求，让读者判断还缺什么条件，再对照推荐结果 |
| P2 | 多框架示例和高级状态 | 在核心模式稳定后，补充不同实现栈或复杂场景的变体 |

首期 P0 不提供账号、云端收藏、评论或任意代码编辑；P1/P2 需先验证读者确实需要。

### 一对多示例：从“做个选择框”出发

先明确：用户要选一个还是多个？选项少且需要同时看见吗？选项很多时是否需要搜索？改动是立即生效还是点击保存后生效？

- 少量选项、必须同时看见、只能选一个：`Radio Group`
- 选项较多、节省页面空间、只能选一个：`Select`
- 少量互斥选项、希望快速切换：`Segmented Control`
- 选项少、可同时看见、允许选多个：`Checkbox Group`
- 可多选且候选很多：`Multi-select`；需要输入过滤时进一步比较 `Combobox`
- 表单里表达是否勾选：`Checkbox`
- 设置偏好并立即生效：`Switch`

每个候选项都解释适用原因，并提供“另一种选择会怎样”的对比链接。若读者尚未说明单选还是多选，系统先把这个条件问清，而不是假装已经确定。

### 内容关系模型

主内容实体不是孤立的术语，而是：

- `PhraseGroup`：一个真实用户目标与若干新手说法，例如“给我个选择框”“放几个选项让用户挑”。
- `Question`：能影响组件选择的澄清问题，例如“可选一个还是多个”。
- `Recommendation`：一组答案成立时的推荐结果，包含一个主要模式、可组合的辅助模式和解释理由。
- `Pattern`：有稳定交互行为的精准模式，如 `Radio Group`、`Select`、`Toast`。
- `Term`：模式的标准名、中文叫法及别名；一个俗称也可能指向多个模式。
- `Demo`：注册表中的安全示例 ID；一个模式可在多个需求页面复用。

关系约束：`PhraseGroup 1 → N Recommendation`；一个 `Recommendation` 可以组合 `1..N Pattern`；一个 `Pattern` 可以被多个 `PhraseGroup` 引用；术语别名可对应多个模式，不能因同名而强行合并。

```yaml
id: choose-value
phrases:
  - 加个选择框
  - 放几个选项让用户挑
userGoal: 让用户从一组候选值中选择类别。
questions:
  - id: cardinality
    prompt: 用户能选几个？
    options:
      - id: one
        label: 只能选一个
      - id: many
        label: 可以选多个
  - id: optionVisibility
    prompt: 选项需要同时显示吗？
    options:
      - id: visible
        label: 需要同时显示
      - id: compact
        label: 节省空间优先
recommendations:
  - when:
      - questionId: cardinality
        optionId: one
      - questionId: optionVisibility
        optionId: visible
    primaryPatternId: radio-group
    supportingPatternIds: []
    reason: 选项不多且必须同时看见，单选组更容易比较。
    alternativePatternIds: [select]
  - when:
      - questionId: cardinality
        optionId: one
      - questionId: optionVisibility
        optionId: compact
    primaryPatternId: select
    supportingPatternIds: []
    reason: 用户只能选一项，且需要节省页面空间。
    alternativePatternIds: [radio-group]
```

推荐条件使用受限、可校验的字段和值，不允许内容作者写可执行 JavaScript。没有答案或多个答案仍符合时，界面显示尚未确定的条件或并列候选。

### 一对多示例：从“加个弹出来的东西”出发

先问它是轻量反馈还是用户需要处理的内容；再问是否要阻断背景、是否锚定于触发元素、内容有多长、主要设备是什么。

- 不需要处理、短暂反馈：`Toast`
- 需要长期可见的页面级提醒：`Banner`
- 需要用户集中完成一项小任务：`Modal Dialog`
- 重要、不可逆的确认：`Alert Dialog`
- 贴着触发控件展示少量上下文内容：`Popover`
- 展示一组操作：`Menu`
- 保留当前列表上下文并从侧边看详情：`Drawer`
- 移动端常用操作从底部展开：`Bottom Sheet`

这些模式仍可以在“术语索引”中直接查找，但它们不会成为主首页的第一层分类。

## 5. 核心用户流程

1. 读者选择一个需求入口，或直接输入自己会说的短句。
2. 系统匹配已整理的常见说法、别名和场景；没有匹配时展示相关入口，不擅自生成答案。
3. 读者回答 1–3 个有实际影响的问题，例如单选/多选、是否阻断、是否立即生效。
4. 系统展示 1–3 个候选模式，并说明推荐原因、替代选择和主要差异。
5. 读者打开 HTML 预览，切换关键状态或比较不同模式。
6. 指令生成器将需求上下文与交互细节拼成一段完整提示词，支持逐项修改和复制。
7. 读者可以继续查看详细术语页，也可以回到需求入口调整答案。

决策流程采用渐进披露：先问最能缩小范围的问题，不在首屏展示术语数量选择器或完整技术分类。

## 6. 内容规划

### 首期内容包

首批框架用 17 个口语案例覆盖 8 个小白需求族，关联 32 个交互模式：

1. **输入信息**：写短名字、写长说明、处理密码或普通文字。
2. **选择和设定**：选分类、勾选标签、设置立即生效还是提交后生效。
3. **执行操作或跳转**：判断当前位置应执行操作还是打开新页面。
4. **反馈**：保存结果、表单校验和多处错误概览。
5. **临时展示内容**：澄清“弹窗”、查看详情、头像入口和移动端分享。
6. **浏览和展开**：切换并列内容或按需展开详情。
7. **查找和整理**：区分搜索结果列表与可选候选值。
8. **页面状态**：加载、初始无内容与搜索无结果。

这些案例是用于搭网站框架的种子内容，不代表最终覆盖面。后续新增内容优先补真实口语表达和能区分交互方向的条件，不以增加术语数量为目标。每个含糊表达至少呈现两个有条件差异的候选结果；条件不足时保留并列候选，不伪装成确定推荐。

### 扩展内容包

扩展到 8 个需求族、约 30–45 个口语入口和 50–70 个模式：操作与导航、内容分组/切换、列表与表格、搜索/过滤/排序、加载/空/错误/完成状态、流程分步与提交。

数字是内容覆盖目标，不是首页让读者选数量。每增加一组内容，先补充真实的新手表达和互相容易混淆的场景，再决定哪些术语值得收入。

### 单个交互模式的内容卡

每个 `Pattern` 至少包含：

- 精确英文术语、常见中文说法和可能造成误会的别名。
- 一句话解释和一个新手会遇到的具体任务。
- 适用条件、不适用条件、关键交互轴，以及与相似模式的差别。
- 1 个可操作示例，以及至少 1 条可复制的 AI 指令。
- 触发、布局、提交方式、结束条件、键盘与焦点行为、窄屏行为。
- `demoId` 和相关口语入口 ID，方便内容与实现双向跳转。

### 首版落地内容结构

首版把这些实体保存在静态 JSON 中：`families.json` 是需求族，`cases.json` 是新手说法、目标、场景、问题和推荐分支，`patterns.json` 是标准术语及说明。案例中的推荐分支按问题 ID 与选项 ID 匹配，使用 `primaryPatternId`、`supportingPatternIds`、`alternativePatternIds` 和 `reason`；模式通过 `demoId` 关联本地预览。新增案例只需沿用内容字段和稳定 ID，不需要编辑页面模板或决策代码。

## 7. 指令生成器

生成器以可编辑的短模板组装信息，不依赖在线模型：

```text
用户目标：{goal}
界面模式：{pattern}
触发方式与位置：{trigger_and_placement}
用户可做的选择或输入：{input_or_choices}
完成、关闭与错误状态：{completion_and_states}
键盘、焦点和窄屏行为：{accessibility_and_responsive}
```

隐藏用户没有选择、且不影响实现的重要性较低的字段；对影响模式选择的字段明确提示补齐。生成结果需要自然、可直接粘贴，读者可以手动改写，不将模式名当成完整需求。

## 8. 首版网站框架和扩展边界

- 当前采用原生 HTML/CSS/JavaScript 与 JSON 的 buildless 静态结构；运行时通过轻量 hash 路由切换需求探索、案例目录和术语索引。
- 纯函数决策引擎读取案例分支；`demo-catalog.js` 用 `demoId` 选择本地原生 HTML 示例；指令生成器组合案例、推荐理由和模式指令。文案数据与页面逻辑分开。
- 案例和术语以 HTTP 静态站点方式读取，因此本地开发需要静态文件服务器；不依赖数据库、账号或模型服务。
- 首版没有引入构建期 schema 校验，也没有 iframe 隔离示例。内容作者不可在 JSON 中写 HTML；模式示例通过本地注册表映射，页面会转义 JSON 文本。
- 当案例量、独立链接需求或内容校验需求显著增长，再评估生成型静态框架与构建期校验。技术迁移应由真实内容规模和维护成本触发，不先让新手内容依赖复杂运行时。

## 8. 首版不做的事

- 不把任何一句中文短语都交给在线 AI 即时判定。
- 不要求用户登录，不存云端用户历史，不采集搜索或提示词。
- 不提供任意用户 HTML/JavaScript 上传和执行。
- 不在早期引入复杂的内容管理后台、评论系统或贡献者账号。
- 不以技术组件清单作为唯一导航，也不要求读者先掌握术语。

## 9. 产品评审标准

- 新手能从一条自己会说的需求开始，不知道术语也能走完整条流程。
- 面对含糊表达，系统能展示多个合理结果及可读的判断理由。
- 相近模式的差别能通过行为和场景说清，而不是只引用技术定义。
- 交互示例可运行，指令覆盖关键行为，窄屏和键盘使用路径完整。
- 内容作者新增一个口语入口或交互模式，不需要改写决策引擎。

## 10. 待维护者评审的决定

1. 是否认可首期范围先覆盖输入/查找、选择/设定、反馈/临时内容三组？
2. 是否认可约 12–15 个口语说法、20–25 个模式作为首期覆盖目标？
3. 是否认可技术方案采用 Astro 静态生成、TypeScript 内容模型和隔离的 HTML 预览？
