# 说准一点：产品与系统设计

- 状态：产品方向已实施为静态首版；此文保留为产品与内容模型基线
- 日期：2026-10-31
- 对应任务：Task Constitution T1、T2、T3
- 设计目标：让不熟悉 UI 术语的人从自己的表达出发，找到合适的交互模式，并把真实需求转成 AI Coding 可执行的指令。

## 1. 产品判断

用户通常不会先想起 `Combobox`、`Alert Dialog` 或 `Disclosure`。他们会说“给我一个选择框”“点一下以后告诉我成功了”“把详情从旁边拉出来”。系统应从这些表达和用户要完成的事开始，再通过少量问题解释多个可能模式的区别。

核心关系是：

```text
新手口语 / 产品需求
        ↓
用户目标与关键条件
        ↓
多个可选交互模式及选择理由
        ↓
术语解释 + 可操作示例 + 精准 AI 指令
```

一个口语入口不必只对应一个术语。相反，同一个交互模式也可以出现在多个不同的需求入口里。因此内容关系采用“多入口到多模式”，并让每条推荐关系带有能读懂的理由。

## 2. 目标用户与需要完成的事

| 用户 | 当前困难 | 希望完成的事 |
|---|---|---|
| 新手产品经理 | 知道业务目的，但只能说“加个弹窗”“做个下拉框” | 发现关键交互差异，写出产品需求或验收标准 |
| AI Coding 新手 | 不确定怎样把想法告诉 AI，也不知道组件名称 | 看见可操作的例子，复制并修改一段清楚的指令 |
| 项目贡献者 | 想补充术语，但容易只添加名词解释 | 按统一模型补齐口语入口、选择条件、模式差异和示例 |

产品不是词典查词练习。读者需要能回答：用户在做什么、界面何时响应、有没有选择、会不会阻断、结果怎样结束。

## 3. 产品原则

1. **从用户目标开始**：首屏用“我想让用户……”或新手原话引导探索。
2. **先解释差异，再教名称**：每个模式都说明“什么情况下适合它”。
3. **模糊时给候选项**：展示少量可比较的结果和推荐理由；必要时再问一题。
4. **指令描述行为**：术语只是提示，指令还应写清触发、位置、选择规则、关闭方式和状态。
5. **例子可以操作**：读者能够直接体验打开、选择、关闭、报错或状态变化。
6. **不用技术背景也能贡献**：内容作者主要填写表单式字段和 Markdown 说明，不必编写决策代码。
7. **静态优先、隐私默认**：教程内容、搜索和需求选择仍在静态站点和浏览器内处理；访问分析通过可选的 Umami Cloud 脚本提供，不增加项目自有后端。

## 4. 信息架构

### 主入口：按我想让用户完成的事来找

| 需求入口 | 新手常用表达示例 | 要回答的主要问题 |
|---|---|---|
| 让用户输入或修改 | “给个文本框”“让用户写一下” | 内容长短、是否搜索、是否私密、是否从已有选项中挑选？ |
| 让用户选择或设定 | “加个选择框”“让他勾一下” | 单选还是多选、选项多少、是否要搜索、是否立即生效？ |
| 让用户执行操作或前往别处 | “加个按钮”“点这里去详情” | 执行动作还是导航、是否主要操作、是否危险、是否有次级操作？ |
| 告诉用户发生了什么 | “提示一下”“报错给我看” | 成功、错误还是提醒？要停留多久？是否需要用户处理？ |
| 临时展示补充内容 | “弹出来”“从旁边拉开详情” | 需要决定吗？阻断背景吗？有锚点吗？从哪个边缘展开？ |
| 浏览、切换和展开内容 | “分几块切换”“点一下再展开” | 同屏展示、互斥切换还是分步查看？ |
| 查找、筛选和整理内容 | “列表里找一下”“加几个筛选条件” | 查关键字、缩小范围、改变排序还是比较记录？ |
| 呈现页面状态 | “加载时显示一下”“没数据怎么办” | 正在加载、首次为空、搜索无结果、失败还是已完成？ |

主导航固定为“按需求找 → 按俗语找 → 按术语找 → 按场景找 → 帮助说明”，顶部菜单是唯一的全站内容浏览入口，不再在页面内容之前重复显示第二排导航。四个浏览入口的数量从 `families.json`、`colloquialisms.json`、`patterns.json` 和 `cases.json` 自动读取并显示在菜单中。底层六类对象还包括 `journeys.json` 的任务脉络与 `sources.json` 的官方来源。需求入口按用户目标归类；俗语把宽泛日常说法拆成多种可能做法；术语页提供准确模式的中文叫法、专业名称和来源；场景页用任务、条件、任务脉络和来源帮助读者判断；帮助页同时为人类和 AI 说明六类对象的字段、关系、编辑顺序和核对标准。

俗语详情遵循“先看效果，再解释”：先并列展示各种做法的中文名称和可操作预览，再说明每种效果是什么、对用户有什么影响、适合什么场景以及需要留意的地方，最后给出可以直接告诉 AI 的中文说法。俗语本身的辨析文字和关键问题放在效果对照之后。默认视图保持紧凑：桌面用多列卡片同时对照更多效果；卡片先显示口语名称、辅助标准名和可操作示例，完整解释通过“了解这个效果”展开。用户点开后能看到适用场景、影响、注意点和可复制的中文指令。窄屏逐步收为两列和单列，降低信息密度时仍保留可读性。

全站优先压缩内容之间的空白和卡片内边距，减少读者滚动比较时的视线跳跃；正文解释保持正常行高，详细信息按需展开。这里的“紧凑”指提高一屏可比较的选项数，不把文字缩小到难以阅读。

### 产品功能分层

| 优先级 | 功能 | 读者得到什么 |
|---|---|---|
| P0 | 口语入口与场景搜索 | 可以按“我想让用户……”或常用说法找到相关需求族 |
| P0 | 俗语一对多映射 | 从“弹框”“文本框”等熟悉说法出发，对照多个做法的样子、效果、适用场景和注意点 |
| P0 | 澄清问题与模式推荐 | 用少量具体问题缩小候选范围；每个结果都解释推荐原因 |
| P0 | 候选比较与关系跳转 | 并排比较相近模式，并查看“如果条件不同，应该选什么” |
| P0 | HTML 交互示例 | 直接体验触发、选择、提交、关闭和异常状态 |
| P0 | 指令生成器 | 把用户目标、行为约束和模式说明整理成可编辑、可复制的指令 |
| P0 | 专业名称辅助索引 | 中文叫法优先呈现，英文标准名称作为补充；可反向找到俗语和案例 |
| P0 | 内容贡献帮助 | 说明需求入口、俗语、术语、场景、任务脉络和来源的维护文件、字段和关联方式 |
| P0 | 贡献说明与内容约定 | 贡献者能按内容契约添加说法、分支、模式和示例关联 |
| P1 | 维护者访问分析 | 在 Umami Cloud 后台查看访问量、页面路径、来源、浏览器、设备和大致地区 |
| P1 | 组合需求 | 例如“搜索并选客户”可以输出 Search Field + Combobox + Empty State 等组合 |
| P1 | 场景练习 | 给出模糊需求，让读者判断还缺什么条件，再对照推荐结果 |
| P2 | 多框架示例和高级状态 | 在核心模式稳定后，补充不同实现栈或复杂场景的变体 |

首期 P0 不提供账号、云端收藏、评论或任意代码编辑；P1/P2 需先验证读者确实需要。

### 一对多示例：从“做个选择框”出发

先明确：用户要选一个还是多个？选项少且需要同时看见吗？选项很多时是否需要搜索？改动是立即生效还是点击保存后生效？

- 少量选项、必须同时看见、只能选一个：`Radio Group`
- 选项较多、节省页面空间、只能选一个：`Select`
- 少量互斥选项、希望快速切换：`Segmented Control`
- 选项少、可同时看见、允许选多个：`Checkbox Group`
- 可多选且候选很多：`Multi-select`；需要输入过滤时进一步比较 `Combobox`
- 表单里表达是否勾选：`Checkbox`
- 设置偏好并立即生效：`Switch`

每个候选项都解释适用原因，并提供“另一种选择会怎样”的对比链接。若读者尚未说明单选还是多选，系统先把这个条件问清，而不是假装已经确定。

### 内容关系模型

主内容实体不是孤立的术语，而是：

- `PhraseGroup`：一个真实用户目标与若干新手说法，例如“给我个选择框”“放几个选项让用户挑”。
- `ColloquialPhrase`：一个更宽泛的日常词或短语，例如“弹框”“文本框”，带有常见变体、解释、区分问题，以及多个模式和案例引用。
- `Question`：能影响组件选择的澄清问题，例如“可选一个还是多个”。
- `Recommendation`：一组答案成立时的推荐结果，包含一个主要模式、可组合的辅助模式和解释理由。
- `Pattern`：有稳定交互行为的精准模式，如 `Radio Group`、`Select`、`Toast`。
- `Term`：模式的标准名、中文叫法及别名；一个俗称也可能指向多个模式。
- `Demo`：注册表中的安全示例 ID；一个模式可在多个需求页面复用。

关系约束：`PhraseGroup 1 → N Recommendation`；`ColloquialPhrase N ↔ N Pattern`；一个 `Recommendation` 可以组合 `1..N Pattern`；一个 `Pattern` 可以被多个需求和俗语入口引用。一个俗语可能对应多种模式，不能因说法相同而强行合并；页面先显示易懂的中文叫法，标准术语放在辅助位置。

```yaml
id: choose-value
phrases:
  - 加个选择框
  - 放几个选项让用户挑
userGoal: 让用户从一组候选值中选择类别。
questions:
  - id: cardinality
    prompt: 用户能选几个？
    options:
      - id: one
        label: 只能选一个
      - id: many
        label: 可以选多个
  - id: optionVisibility
    prompt: 选项需要同时显示吗？
    options:
      - id: visible
        label: 需要同时显示
      - id: compact
        label: 节省空间优先
recommendations:
  - when:
      - questionId: cardinality
        optionId: one
      - questionId: optionVisibility
        optionId: visible
    primaryPatternId: radio-group
    supportingPatternIds: []
    reason: 选项不多且必须同时看见，单选组更容易比较。
    alternativePatternIds: [select]
  - when:
      - questionId: cardinality
        optionId: one
      - questionId: optionVisibility
        optionId: compact
    primaryPatternId: select
    supportingPatternIds: []
    reason: 用户只能选一项，且需要节省页面空间。
    alternativePatternIds: [radio-group]
```

推荐条件使用受限、可校验的字段和值，不允许内容作者写可执行 JavaScript。没有答案或多个答案仍符合时，界面显示尚未确定的条件或并列候选。

### 一对多示例：从“加个弹出来的东西”出发

先问它是轻量反馈还是用户需要处理的内容；再问是否要阻断背景、是否锚定于触发元素、内容有多长、主要设备是什么。

- 不需要处理、短暂反馈：`Toast`
- 需要长期可见的页面级提醒：`Banner`
- 需要用户集中完成一项小任务：`Modal Dialog`
- 重要、不可逆的确认：`Alert Dialog`
- 贴着触发控件展示少量上下文内容：`Popover`
- 展示一组操作：`Menu`
- 保留当前列表上下文并从侧边看详情：`Drawer`
- 移动端常用操作从底部展开：`Bottom Sheet`

这些模式仍可以在“术语索引”中直接查找，但它们不会成为主首页的第一层分类。

## 5. 核心用户流程

1. 读者选择一个需求入口，或直接输入自己会说的短句。
2. 系统匹配已整理的常见说法、别名和场景；没有匹配时展示相关入口，不擅自生成答案。
3. 读者回答 1–3 个有实际影响的问题，例如单选/多选、是否阻断、是否立即生效。
4. 系统展示 1–3 个候选模式，并说明推荐原因、替代选择和主要差异。
5. 读者打开 HTML 预览，切换关键状态或比较不同模式。
6. 指令生成器将需求上下文与交互细节拼成一段完整提示词，支持逐项修改和复制。
7. 读者可以继续查看详细术语页，也可以回到需求入口调整答案。

决策流程采用渐进披露：先问最能缩小范围的问题，不在首屏展示术语数量选择器或完整技术分类。

## 6. 内容规划

### 首期内容包

首批框架用 17 个口语案例覆盖 8 个小白需求族，关联 32 个交互模式：

1. **输入信息**：写短名字、写长说明、处理密码或普通文字。
2. **选择和设定**：选分类、勾选标签、设置立即生效还是提交后生效。
3. **执行操作或跳转**：判断当前位置应执行操作还是打开新页面。
4. **反馈**：保存结果、表单校验和多处错误概览。
5. **临时展示内容**：澄清“弹窗”、查看详情、头像入口和移动端分享。
6. **浏览和展开**：切换并列内容或按需展开详情。
7. **查找和整理**：区分搜索结果列表与可选候选值。
8. **页面状态**：加载、初始无内容与搜索无结果。

这些案例是用于搭网站框架的种子内容，不代表最终覆盖面。后续新增内容优先补真实口语表达和能区分交互方向的条件，不以增加术语数量为目标。每个含糊表达至少呈现两个有条件差异的候选结果；条件不足时保留并列候选，不伪装成确定推荐。

### 当前内容覆盖（2026-10-31）

当前内容包括 17 个需求族、161 个需求场景、128 个俗语检索表达、72 个交互模式、8 条任务脉络和 51 个去重来源。场景和模式通过官方来源 ID 连接参考依据；新增六类需求族均由多条任务场景支持。中文需求语句和俗语检索表达是基于指南编写的教学示例，不冒充研究访谈原话。数字用于描述当前覆盖，不代表模式完整，也不作为新增术语的配额。

每增加一组内容，先补充真实的新手表达和互相容易混淆的场景，再决定能否复用现有术语。每个含糊表达至少呈现两个有条件差异的候选结果；条件不足时保留并列候选，不伪装成确定推荐。

本轮新增内容的来源与边界见 `docs/content-research.md`。内容经 WAI-ARIA APG、GOV.UK Design System 和 USWDS 官方指引交叉核对；站内说明为中文概括，不直接复制组件库代码或设计样式。

### 大内容集的呈现

六份静态 JSON 在启动时并行读取，搜索与筛选在完整的 161 条轻量场景数据上执行。当前六份数据合计约 425 KB（425,014 字节，未压缩）。结果目录按 12 个场景、18 个俗语、24 个术语分批展示；术语详情的关联场景每次仅呈现 6 条；俗语详情中的交互示例滚动到视口附近时再挂载。筛选变化后回到第一页。来源标题和 URL 存在去重目录，避免每个场景重复保存。若移动设备上实测出现网络或 JSON 解析瓶颈，再按任务脉络拆分静态文件并保留全局搜索能力。

### 单个交互模式的内容卡

每个 `Pattern` 至少包含：

- 精确英文术语、常见中文说法和可能造成误会的别名。
- 一句话解释和一个新手会遇到的具体任务。
- 适用条件、不适用条件、关键交互轴，以及与相似模式的差别。
- 1 个可操作示例，以及至少 1 条可复制的 AI 指令。
- 触发、布局、提交方式、结束条件、键盘与焦点行为、窄屏行为。
- `demoId` 和相关口语入口 ID，方便内容与实现双向跳转。

### 首版落地内容结构

首版把这些实体保存在静态 JSON 中：`families.json` 是按用户目标归纳的需求入口，`journeys.json` 是官方服务任务归纳出的浏览脉络，`cases.json` 是具体场景、目标、条件问题、推荐分支和来源 ID，`sources.json` 是去重的官方参考链接，`colloquialisms.json` 是俗语到多个模式和场景的映射，`patterns.json` 是模式中文叫法、标准名称及说明。帮助页按这些内容类型说明编辑位置和关联方法；完整贡献约定仍放在 `CONTRIBUTING.md`。案例中的推荐分支按问题 ID 与选项 ID 匹配，使用 `primaryPatternId`、`supportingPatternIds`、`alternativePatternIds` 和 `reason`；模式通过 `demoId` 关联本地预览。新增场景或俗语可沿用数据字段和稳定 ID，优先复用已有模式。

## 7. 指令生成器

生成器以可编辑的短模板组装信息，不依赖在线模型。中文叫法、用户目标、使用场景、交互效果和注意点优先出现；标准术语只作为可查阅的辅助信息：

```text
用户目标：{goal}
界面做法：{plain_language_pattern_name}
触发方式与位置：{trigger_and_placement}
用户可做的选择或输入：{input_or_choices}
完成、关闭与错误状态：{completion_and_states}
键盘、焦点和窄屏行为：{accessibility_and_responsive}
```

隐藏用户没有选择、且不影响实现的重要性较低的字段；对影响模式选择的字段明确提示补齐。生成结果需要自然、可直接粘贴，读者可以手动改写，不将模式名当成完整需求。

## 8. 首版网站框架和扩展边界

- 当前采用原生 HTML/CSS/JavaScript 与 JSON 的 buildless 静态结构；运行时通过轻量 hash 路由切换需求探索、俗语索引与详情、案例目录和专业术语索引。
- 部署目标是传统静态文件托管，分享仓库或静态站点链接即可；不建设项目自有数据库、账号系统、应用后端或远程 AI API。原生 JavaScript 只用于需要交互的浏览器行为和可选的第三方页面访问统计。
- 纯函数决策引擎读取案例分支；俗语数据以 `patternIds` 和 `caseIds` 连接内容；`demo-catalog.js` 用 `demoId` 选择本地原生 HTML 示例；指令生成器组合案例、中文叫法、推荐理由和模式指令。文案数据与页面逻辑分开。
- 案例和术语以 HTTP 静态站点方式读取，因此本地开发需要静态文件服务器；不依赖数据库、账号或模型服务。
- 首版没有引入构建期 schema 校验，也没有 iframe 隔离示例。内容作者不可在 JSON 中写 HTML；模式示例通过本地注册表映射，页面会转义 JSON 文本。
- 当案例量、独立链接需求或内容校验需求显著增长，再评估生成型静态框架与构建期校验。技术迁移应由真实内容规模和维护成本触发，不先让新手内容依赖复杂运行时。

## 9. 访问数据分析

访问分析由 Umami Cloud 托管。主站只有在 `src/lib/analytics-config.js` 中填写网站 ID、且访问域名在允许列表内时才加载统计脚本；网站 ID 是公开标识，不是秘密。空 ID 会关闭统计。

当前只启用页面浏览统计。脚本尊重浏览器的 Do Not Track 设置、排除 URL 查询参数，并保留本项目的 hash 路由用于区分需求、俗语、术语和场景页。站内搜索词、AI 指令文本、示例控件输入值和自定义点击事件都不发送。统计失败或被拦截不会影响教程功能。

Umami 使用访问者 IP 地址和浏览器信息生成匿名会话，并可估算地区；其标准分析记录不保存原始 IP，但服务商及其处理商可能为运行、安全等目的处理网络数据。读者可从页脚打开 Umami 隐私说明；数据保留、服务器区域和其他处理细节以 Umami Cloud 账户当时适用的条款为准。站点所有者需要自行创建并保管 Umami 账户；历史访问量无法回填。配置步骤见 [`docs/analytics-setup.md`](analytics-setup.md)。

## 10. 首版不做的事

- 不把任何一句中文短语都交给在线 AI 即时判定。
- 读者不需要登录，教程不保存个人进度；访问分析仅按第 8 节统计匿名页面会话，不采集搜索内容或提示词。
- 不提供任意用户 HTML/JavaScript 上传和执行。
- 不在早期引入复杂的内容管理后台、评论系统或贡献者账号。
- 不以技术组件清单作为唯一导航，也不要求读者先掌握术语。

## 11. 产品评审标准

- 新手能从一条自己会说的需求开始，不知道术语也能走完整条流程。
- 面对含糊表达，系统能展示多个合理结果及可读的判断理由。
- 相近模式的差别能通过行为和场景说清，而不是只引用技术定义。
- 交互示例可运行，指令覆盖关键行为，窄屏和键盘使用路径完整。
- 内容作者新增一个口语入口或交互模式，不需要改写决策引擎。

## 12. 历史首版假设与当前实现

早期规划提出先覆盖三组需求、约 12–15 个口语说法和 20–25 个模式，并评估 Astro、TypeScript 与隔离预览。这些是尚未采纳的历史方案，不再作为当前范围：目前采用 17 个需求族、128 条口语检索表达、72 个模式、161 个场景与原生静态文件，并通过本地预览注册表呈现示例。后续是否迁移技术栈，应依据真实性能与维护瓶颈决定。
